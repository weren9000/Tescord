# Шифрование Квачата

Опубликовано 2 ноября 2026 на kvachat.ru: код приложения `a0d2d43404f51986621ff32630d58b4f59dc391a`, Windows 0.5.33 и Android 0.3.36 (versionCode 40). Подпись Android совпадает с 0.3.35. Рабочие данные перенесены в зашифрованное хранение; секретные чаты и шифрование звонков включены. Используется модель обычной облачной переписки и отдельных секретных чатов, а не протокол Telegram MTProto.

## Границы защиты

| Режим | Кто располагает ключами | Восстановление | История и поиск |
| --- | --- | --- | --- |
| Обычные чаты и сообщения комнат | Сервер, отдельно от БД | Администратор с защищённой копией ключей | Существующие клиенты, серверный поиск |
| Секретная личная переписка | Только два выбранных устройства | Сервер восстановить не может | Локальная история и поиск |
| Медиа звонков при включённом режиме E2EE | Только подтверждённые устройства текущего звонка | Не применяется | Аудио, камера и демонстрация; ключи только в памяти |

Обычный режим защищает отдельную утечку БД/файлов без ключей. Он не скрывает содержание от работающего сервера или администратора с ключами. Идентификаторы, участники, время, размеры, обычные имена вложений и служебные поля остаются открытыми. Поисковый индекс скрывает подстроки, но раскрывает повторения и частоты.

Секретный режим скрывает содержание, имена и ключи файлов от сервера. Сверка кода между участниками обнаруживает подмену открытого ключа. Это не защита от заражённого устройства, сохранённых получателем копий или подменённого JavaScript веб-клиента. Метаданные доставки, участники, время и объём остаются видимыми серверу.

## Обычная переписка

Миграция `0057`: шифротекст сообщений, индекс поиска, признаки шифрования файлов комнат, контрольные записи ключей и журнал очистки старых файлов. Колонка `content` сохраняется для старой истории; после переноса она пустая. Ограничение БД запрещает одновременное сохранение открытого текста и шифротекста. Новые записи шифруют обработчики SQLAlchemy.

Текст: AES-256-GCM, случайный 256-битный salt и отдельный ключ HKDF каждого конверта, идентификатор ключа, привязка к таблице/записи через AAD. Файл: отдельный ключ HKDF, аутентифицированный заголовок с размером, части по 1 МиБ и отдельные nonce. Точная длина контейнера обязательна. `.kvaenc` никогда не трактуется как открытый файл. Чтение и HTTP Range ограничены по памяти; поддерживается один диапазон, несколько отклоняются. Повреждение последующей части прекращает поток.

Фото-превью также зашифрованы; текстовые предпросмотры читают расшифрованный поток. Redis-события защищены отдельными конвертами. Очередь уведомлений хранит ссылки на сообщения. Обычные push могут содержать текст по существующим настройкам уведомлений.

Поиск использует HMAC по n-граммам, затем проверяет расшифрованные кандидаты постранично. Старые ключи поддерживаются до завершения ротации. Это компромисс между защитой индекса и существующим поиском по подстроке.

## Ключи и перенос данных

`TESCORD_DATA_KEYRING_PATH` — абсолютный путь к приватному файлу вне релизов. В production он обязателен независимо от `TESCORD_DATA_ENCRYPTION_REQUIRED`. Development допускает открытые локальные фикстуры без ключа. Реальные ключи, пароли и runtime-конфигурацию нельзя помещать в Git, публичные архивы, логи или отчёты.

Команды из `backend`:

```text
python -m app.encryption_admin init --keyring <приватный-файл>
python -m app.encryption_admin status
python -m app.encryption_admin migrate --offline
python -m app.encryption_admin verify
python -m app.encryption_admin rotate-key --keyring <приватный-файл>
python -m app.encryption_admin rotate-data --offline
```

Каталог ключа создаётся заранее с приватными правами. `init` не перезаписывает файл. Ротация добавляет ключ и сохраняет старые. Контрольные записи БД обнаруживают потерю/замену ключа и блокируют запуск или чтение. Вывод и журнал операций содержат только статусы и счётчики. Если каталог принадлежит root и доступен группе приложения только для чтения, заранее создать файл `<keyring>.audit.jsonl` с владельцем `tescord` и режимом `0600`; самому приложению запись в каталог ключей не предоставлять. Ошибка записи аудита может возникнуть уже после завершения переноса: перед повторным запуском проверить `status`, а не считать данные неизменёнными.

Перед переносом остановить все API/фоновые процессы, сделать согласованную копию БД и файлов, проверить её восстановление и наличие ключа на отдельном носителе. `--offline` — подтверждение оператора, не автоматическая остановка сервиса. Advisory lock запрещает параллельные миграции. Перенос идёт пакетами; файл проверяется до смены указателя, удаление прежнего файла записывается в журнал той же транзакцией. Прерванный перенос можно повторить.

После переноса проверить нулевые счётчики открытых записей/очистки и выполнить `verify`. Все новые workers перезапускаются одновременно: старые не понимают зашифрованные Redis-события. Возврат к backend без поддержки шифрования после появления зашифрованных данных запрещён. Для возврата старого релиза нужна согласованная проверенная копия и обслуживание. Alembic downgrade отказывается удалять защищённые данные.

Перенос не стирает прежние plaintext-backup, журналы PostgreSQL, снимки диска и освобождённые страницы файловой системы. Перед рабочим включением отдельно инвентаризировать старые копии и определить их защищённое хранение/удаление; `verify` проверяет текущие логические данные, а не гарантированное физическое стирание носителя.

## Резервные копии

`backup-server.sh` требует age и файл публичных получателей. Приватный age-ключ восстановления хранится отдельно от сервера. БД, файлы и конфигурация идут потоком в age без открытых промежуточных архивов. Реально настроенный data keyring включается в отдельный зашифрованный архив конфигурации. Архива БД самого по себе недостаточно для чтения переписки.

Ключей секретных чатов на сервере нет. Таблицы `secret_*`, файлы секретных загрузок и временные комнаты исключены из резервирования. `COMPLETE` создаётся после успеха всех архивов и проверки SHA-256. Контрольные суммы не заменяют проверку расшифрования age. Ранее созданные открытые копии автоматически не перекодируются; их защита и сроки хранения проверяются отдельно. Старый ключ нельзя удалять, пока он требуется сохранённой копии.

Восстановление проверяется в изолированной среде: суммы → расшифрование age → конфигурация/data keyring с приватными правами → PostgreSQL/файлы → `verify` → чтение, поиск и скачивание тестовых данных. Для согласованного снимка первого переноса сервис останавливается. Обычный архив работающего сервера не является атомарным снимком БД и файлов.

## Секретные чаты

`TESCORD_SECRET_CHATS_ENABLED` по умолчанию выключен. Миграция `0058` создаёт отдельные устройства, подписанные одноразовые ключи, чаты, конверты и загрузки. Обычные API сообщений не адресуют секретные чаты.

Криптография: `@matrix-org/matrix-sdk-crypto-wasm` 18.9.0, Olm/Megolm. Это адаптер доставки, не Matrix homeserver. Подписанные публичные ключи проверяются сервером и SDK. Выбранные два устройства неизменны; сначала участники сверяют код. Передача ключей другим устройствам, автоматическое восстановление и key backups отключены. Megolm меняет ключ по времени/числу сообщений и позволяет читать локальную историю повторно после перезапуска.

Состояние SDK находится в зашифрованной IndexedDB. Пароль хранилища защищён Windows safeStorage/DPAPI или Android Keystore. Браузер использует неэкспортируемый CryptoKey в IndexedDB; он не защищает от вредоносного кода на том же origin. Web Locks допускает одну вкладку с crypto store; операции сериализованы.

До подтверждения доставки конверт сохраняется локально. Исходящий UUID устойчив к перезагрузке; повторы с иным содержимым отклоняются. После подтверждения сервер удаляет тело, оставляя квитанцию идемпотентности. Поиск работает по истории устройства. Черновик находится только в памяти: закрытие диалога его сохраняет, перезапуск приложения — нет.

Файл шифруется на устройстве AES-256-GCM частями по 1 МиБ. Случайный ключ, имя и MIME находятся внутри сообщения Megolm. AAD связывает идентификатор, полный размер, число частей и индекс. Максимум 500 МиБ; пустой файл тоже аутентифицирован. Сервер проверяет пару устройств, владельца, размеры, квоту и повторные записи. Неопубликованные загрузки удаляются через сутки. Файлы доступны пока открыт чат; при завершении/отзыве очередь и файлы удаляет фоновая очистка. Прочитанная история и уже скачанные копии получателя остаются.

Windows/Android сохраняют части через системный выбор места. Браузер использует File System Access API; без него fallback ограничен 8 МиБ. Фото до 8 МиБ расшифровываются только локально. При отмене/ошибке сохранение не завершается; Android-провайдер документов может иметь свои правила удаления незавершённого документа.

Уведомления: только «Новое секретное сообщение». Web Push привязан к сессии устройства; Windows проверяет очередь локально, Android использует фоновую службу. Работа зависит от разрешений и доступности фоновой службы.

Явный выход с предупреждением удаляет локальные ключи/историю и отзывает устройство. Истечение авторизации только блокирует хранилище. При повторном входе SDK подписывает одноразовый запрос сервера, связанный с новой сессией и сроком 120 секунд. Новый access token без прежнего закрытого ключа не присваивает устройство. Отозванное устройство или отозванная прежняя сессия так не восстанавливаются.

## Звонки

`TESCORD_MEDIA_ENCRYPTION_ENABLED` по умолчанию выключен. При включении API требует версию протокола клиента `olm-livekit-v1`; старый клиент получает 426 до выдачи доступа к медиа. Личные звонки, голосовые каналы групп/площадок и комнаты с гостями используют один модуль и общий компонент проверки. Это не сигнализация Telegram и не реализация MTProto.

Каждый вход создаёт новую временную Olm-идентичность, подписанные одноразовые ключи и независимый случайный ключ отправителя LiveKit. Закрытые ключи не пишутся в БД, IndexedDB или резервную копию. Устройства участников автоматически допускаются к обмену после проверки подписей, привязки к комнате и присутствия в LiveKit. Принадлежность ключей участникам определяется через авторизованный каталог сервера; независимой сверки личности по доверенному каналу нет. Локальный флаг Verified в Olm SDK означает разрешение на доставку, а не ручную проверку пользователем. Ключи передаются внутри Olm-конвертов; сервер не получает открытый ключ медиа. Внутренний отпечаток состава включает комнату, идентичности и публичные ключи всех участников и используется для привязки конвертов, но в интерфейсе не показывается.

При входе/выходе участника, смене устройства или переподключении отправители меняют ключи и сбрасывают прежние ключи приёма. Новый обмен проходит автоматически; до установки ключей кадры отбрасываются. Изменение ключа под прежним идентификатором устройства отклоняется; новый вход создаёт новый идентификатор. Если каталог уже доставил конверт, а LiveKit ещё не объявил отправителя, клиент сохраняет конверт в очереди сервера до появления участника. Ключ от известного отправителя для будущего состава сохраняется только в памяти до соответствующего события LiveKit. На устройство хранится максимум один ожидающий ключ, номер последнего полученного поколения сохраняется при смене состава для отклонения повторов. Использованные и отменённые буферы обнуляются. Проверки текущего состава после асинхронных операций не позволяют завершить допуск для устаревшего состава. Незашифрованная дорожка останавливает звонок, неподдерживаемый WebView получает ошибку без перехода к открытому медиа.

Миграция `0059`: временные публичные устройства и очереди Olm-конвертов `secret_media_*`. Токен обмена ключами отделён от аккаунтного JWT и на каждом запросе перепроверяет допуск к конкретному звонку, включая гостя. Отзыв сессии, выход гостя и завершение встречи закрывают доступ. Одноразовые ключи не выдаются повторно; квитанции идемпотентности не содержат тело после ACK. Устройства без heartbeat пять минут удаляются вместе с очередью. Эти таблицы не входят в резервные копии.

В интерфейсе показан компактный индикатор: подготовка соединения, «Звонок зашифрован» или ошибка обмена ключами. Подробности открываются нажатием и закрываются Escape. Названия, участники, время и сетевые метаданные звонка остаются видимыми инфраструктуре. Автоматическое доверие каталогу не защищает от подмены личности скомпрометированным сервером, записи собеседником или скомпрометированного клиента.

Формат `olm-livekit-v1` сохранён. Старые приложения продолжают требовать ручное подтверждение со своей стороны; для полностью автоматических звонков нужно обновить браузерную сборку, Windows и Android. Изменение не требует миграции БД или смены серверных ключей.

Проверки оформления включают обе темы и ширины 320/393/1024 px; основные кнопки общего звонка остаются в одном ряду. Нативные smoke-сценарии проверяют автоматический обмен, реальный входящий PCM и видео в Electron и Android WebView.

Общий helper запрещает внешние API и проверяет имя тестовой БД/домены аккаунтов. `scripts/encryption-restore-smoke.py` использует локальные PostgreSQL/age из `.tools` и создаёт отдельную БД восстановления.

Windows: сначала сборка desktop, затем `node scripts/encryption-native-smoke.cjs windows` и `node scripts/encryption-windows-call-smoke.cjs`. Android: `node mobile/prepare-web.cjs`, `npm run sync --prefix mobile`, сборка debug с отдельным applicationId `ru.kvachat.encryptioncheck`, установка только этой тестовой сборки, разрешения и запуск. Затем `encryption-native-smoke.cjs android`, `encryption-android-save-smoke.cjs`, `encryption-android-call-smoke.cjs`. Последнему нужны работающий сетевой интерфейс эмулятора, adb и локальный SFU. После проверки удалить тестовый пакет, снять adb forwarding и закрыть эмулятор. Не устанавливать тестовую сборку поверх пользовательского приложения.

## Включение на рабочем сервере

Публикация выполнена после восстановления доступности сервера. Перед переносом остановлены все API workers, создана и проверена восстановлением согласованная age-копия. Приватный ключ восстановления сохранён на ПК администратора, включая защищённую копию вне каталога проекта; на сервер передан только публичный age-получатель. Отдельный приватный data keyring хранится вне релизов. API запущен после офлайн-миграции и `verify`.

Проверены 142 сообщения и 50 файлов; все счётчики открытых сообщений, старых файлов, BLOB и незавершённой очистки равны нулю. Сравнение хешей расшифрованных сообщений подтвердило сохранность исходного текста; поиск по существующей переписке прошёл проверку без тестовых записей в рабочих аккаунтах. Также зашифрованы 27 исторических архивов (около 1,33 ГБ), открытых архивов в каталоге резервирования не осталось. Для контрольных исторических архивов БД и конфигурации проверено расшифрование с совпадением исходных SHA-256. Это не стирает прежние данные из WAL и освобождённых секторов диска.

Оба E2EE-флага включены. Все основные systemd-службы, nginx и календарь работают; ревизия календаря сохранена. Публичный health, хеши опубликованных bundle-файлов и крипторесурсов, размеры и контрольные суммы установщиков совпали с локальной сборкой. В production-браузере без подмены API проверены страницы входа/скачивания, компиляция WASM и запуск media worker. Для `.mjs` в nginx задан JavaScript MIME-тип: стандартный `application/octet-stream` блокирует module worker. Исправление применено к действующей конфигурации и внесено в шаблоны развёртывания.

Старые клиенты для звонков требуют обновления до Windows 0.5.33 / Android 0.3.36; веб-клиенту нужна перезагрузка страницы. Реальные обмены секретными сообщениями и звонки проверены ранее в изолированном окружении, а не на рабочих аккаунтах. Проверка на физических телефонах и независимый аудит криптографической интеграции остаются отдельными проверками перед широким выпуском.
