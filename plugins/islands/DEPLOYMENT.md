# Установка независимого сервиса «Острова»

Публикация выполняется по отдельному запросу. Для открытия игры нужны оболочки с разрешённым игровым iframe: Windows 0.5.34+ и Android 0.3.37+. Состояние установленной ревизии проверяется по `SOURCE_REVISION`, службе и публичным путям после деплоя.

## Изоляция и состав

Сервис запускается отдельным пользователем `kva-islands`, одним процессом Uvicorn, с собственным виртуальным окружением. Он не импортирует основной backend, не получает его JWT-секрет, SMTP, доступ к PostgreSQL/Redis или приватный ключ выдачи разрешений. Доступ к API чата игровому процессу не требуется.

Рекомендуемое размещение:

- `/srv/tescord/plugins/islands/current` — ссылка на текущий каталог релиза, код доступен сервису только для чтения;
- `/srv/tescord/plugins/islands/releases/<revision>` — `islands/`, `web/`, `pyproject.toml` и описание ревизии;
- `.venv` внутри каждого каталога релиза — отдельное окружение Python 3.13; откатывается вместе с кодом;
- `/srv/tescord/plugins/islands/data/islands.sqlite3` — собственная БД вне релизов;
- `/etc/kvachat/islands.env` — параметры сервиса, пример в `deploy/islands.env.example`.

`art/source`, `art/prompts*`, `tests`, тестовые маршруты `/_test`, кэши, локальные конфигурации и секреты в серверный архив не включать. Из чистого закоммиченного checkout выполнить `python plugins/islands/scripts/package-release.py <archive.tar.gz>`: упаковщик берёт runtime и файлы установки по белому списку и добавляет ревизию и контрольные суммы. Основной `scripts/package-release.py` исключает этот независимый плагин целиком.

Каталог `web` должен оставаться рядом с Python-пакетом `islands`: сервис запускается из `current`. Один установленный wheel без `web` недостаточен. Зависимости устанавливать командой `.venv/bin/pip install -r requirements.lock` в окружение конкретного релиза. WebSocket-транспорт включён отдельной зависимостью. Зафиксировать `pip freeze` вместе с ревизией; рабочее окружение чата не менять.

В `releases` оставлять текущую версию и не более двух резервных. Перед очисткой разрешать реальные пути, проверять, что они внутри каталога релизов, и исключать `current` и `data`. Не хранить на сервере исходные PNG, повторные архивы, тестовые сборки и десятки старых релизов.

## Ключи и настройки

Создать отдельную пару Ed25519 скриптом `scripts/create-grant-key.py`, указав `--private` и `--public` вне репозитория/релизного архива. Скрипт не перезаписывает существующие файлы и не выводит ключи. Приватный файл читается только пользователем основного backend; открытый доступен `kva-islands`. На Linux права приватного файла — 0600, каталога с ним — 0700. На Windows ограничить ACL владельцем.

В настройках основного backend добавить `TESCORD_ISLANDS_GRANT_PRIVATE_KEY_PATH` с локальным серверным путём. `TESCORD_ISLANDS_ENABLED` оставить `false`, пока отдельный сервис и HTTPS-прокси не проверены.

В игровом env задать `ISLANDS_DATABASE`, `ISLANDS_GRANT_PUBLIC_KEY_PATH`, точные `ISLANDS_ALLOWED_ORIGINS` и `ISLANDS_ALLOWED_HOSTS`. Для текущих оболочек это `https://kvachat.ru` и Android `https://localhost`; Windows использует origin `https://kvachat.ru`. Не ставить `*`. Для разработки разрешать только конкретные localhost/127.0.0.1 с портом.

У основного и игрового процессов должны быть синхронизированы часы. При ротации сначала подготовить пару, кратко остановить выдачу новых разрешений, сменить открытый ключ игры и приватный ключ backend согласованно, затем возобновить. Уже открытые сессии живут не дольше 90 секунд после последней выдачи разрешения.

## Служба и HTTPS

`deploy/kva-islands.service` содержит готовую службу systemd: порт 8013 только на loopback, один worker, размер WebSocket-кадра 2048 байт, лимит соединений и прав записи. Создать пользователя без shell, каталог `data` с владельцем `kva-islands` и правами 0700, установить зависимости и unit. Сервис должен успешно ответить на `http://127.0.0.1:8013/health`.

Фрагмент `deploy/nginx.conf` включается в существующий HTTPS server. Он использует существующую http-level переменную `$kva_connection`, удаляет `/plugins/islands/` при передаче в Uvicorn и передаёт реальный IP клиента. Доверять proxy headers только loopback-прокси; не открывать 8013 наружу. Uvicorn запускается с `--root-path /plugins/islands`.

Перед reload выполнить `nginx -t`. Проверить HTTPS `/plugins/islands/health`, `/plugins/islands/play.html`, `/plugins/islands/api/config` и отказ доступа к `/_test/`, `art/source/` и неизвестным API. У игрового пути не должно остаться унаследованного `X-Frame-Options: SAMEORIGIN`: он мешает Android. Вместо него сервис выставляет CSP `frame-ancestors` с точными разрешёнными origin. Запрещены inline scripts, внешние скрипты, камера и микрофон внутри игры. Проверить заголовки снаружи, а не только конфигурационный файл.

После проверки включить `TESCORD_ISLANDS_ENABLED=true` в основном backend и перезапустить его по обычной процедуре релиза. Пользователь подключает «Острова» в каталоге приложений. Прежде чем объявлять релиз готовым, проверить вход, комнату трёх пользователей, скрытые руки, переподключение и сохранение после перезапуска игрового сервиса. Проверить новую Windows/Android-оболочку: старый CSP и старый Android WebViewClient запрещают iframe. Локальный тест Android WebView с возвратом после 95 секунд фона уже проходит; реальный звонок и работу с опубликованным сервером нужно проверить при выпуске. После проверки эмулятор закрыть.

## Разрешения и границы

Основной backend проверяет обычную авторизацию и подключение приложения. Grant одноразовый, живёт 60 секунд, содержит только `iss`, `aud`, `sub`, `nick`, `iat`, `exp`, `jti`; подпись Ed25519, без выбора алгоритма клиентом. Обмен создаёт случайную сессию, ограниченную 90 секундами от выдачи grant. Родитель обновляет grant каждые 40 секунд. Отзыв основной сессии/отключение приложения блокирует следующее обновление; остаточное окно — не более 90 секунд. Это ограниченный отзыв, не мгновенный.

Токен игры находится только в памяти iframe и передаётся в Authorization или первом WebSocket-сообщении, никогда в URL. В БД хранится SHA-256 токена. `postMessage` проверяет origin и конкретное окно с обеих сторон. Игра — доверенный код Квачата на том же origin; iframe не является границей изоляции от скомпрометированного собственного frontend. Нельзя подменять этот экран произвольными сторонними приложениями.

Каждый HTTP-запрос проверяет сессию; каждое WebSocket-обновление — срок сессии и участие в комнате. Из внутреннего состояния выдаётся белый список полей: только собственные ресурсы/карты; у других — количества и публичные очки. Кубики и колоду задаёт сервер. Транспорт — HTTPS/WSS; скрытые руки хранятся в собственной БД на сервере, это не сквозное шифрование игры.

Лимиты: 8 КиБ тела, таймаут чтения, 1200 HTTP API-запросов/мин на IP, 240 авторизованных/мин на пользователя, 120 WS-подключений/мин на IP, четыре WS на пользователя, 120 кадров/мин, пять незавершённых партий на пользователя. Лимит действий комнаты — 20000, после него остаётся завершение голосованием. Ограничители находятся в памяти одного worker. Для нескольких процессов/узлов нужны общий limiter и новое решение хранения/уведомлений; простое увеличение `--workers` не поддерживается.

Журнал не содержит рук, токенов или полного тела команд. Отладочные HTTP/WS-логи с телами и Authorization не включать. API отвечает `no-store`, HTML/JS/CSS проверяются на обновление через `no-cache`, иллюстрации кэшируются на час.

## Резервирование и откат

SQLite работает в WAL. Для согласованной копии применять `sqlite3.Connection.backup()` либо остановить сервис и сохранить весь набор БД/WAL/SHM. Копирование одного активного `.sqlite3` может потерять последние ходы. Резервные копии содержат скрытые руки и идентификаторы пользователей; хранить с ограниченными правами и проверять восстановление в отдельной папке.

`Store.prune(days=30)` — явная операция обслуживания: удаляет только завершённые/отменённые партии старше срока, включая события и квитанции каскадно. Неактивные, но незавершённые партии автоматически не удаляются. Минимальный срок метода — семь дней. Запускать отдельно после резервной копии, с тем же пользователем и путём БД.

Для отката сначала выключить запись каталога флагом, остановить сервис, вернуть `current` на проверенную резервную ревизию и запустить. В этой версии схема создаётся через `CREATE TABLE IF NOT EXISTS`, правил миграции более новых состояний назад нет: будущие изменения схемы/ruleset должны включать отдельный план совместимости. Не заменять рабочую БД тестовой и не удалять `data` при очистке релизов.
