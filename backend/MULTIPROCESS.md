# Несколько процессов API

Для production нужен общий Redis (`TESCORD_REDIS_URL`) и PostgreSQL. Без Redis
разрешён только локальный режим одного процесса. Пример systemd —
`infra/systemd/tescord-backend.service.example`.

## Состояние и доставка

* Сообщения, заявки, кошельки, покупки и инвентарь остаются в PostgreSQL. Outbox
  забирает партии через `FOR UPDATE SKIP LOCKED`; повтор доставки безопасен по ID сообщения.
* События приложения доставляются Redis Pub/Sub всем процессам; каждый выбирает
  свои подключения и проверяет права. ID события подавляет повторную доставку.
  При восстановлении транспорта клиент получает `resync_required` и перечитывает данные.
* Голосовые участники, подключения устройств, владельцы личных звонков и сроки
  ожидания общие. WATCH/MULTI атомарно изменяет состояние и добавляет события в
  ограниченный Redis Stream. Каждый процесс читает поток по собственному курсору;
  событие доставляется только указанным локальным WebSocket.
* Процесс обновляет lease каждые 5 секунд, срок — 30 секунд. После исчезновения
  процесса устаревшие голосовые подключения удаляются. Для личного звонка после
  исчезновения устройства есть ещё 20 секунд на восстановление того же client_id.
  Живое второе подключение того же устройства не завершает звонок.
* Онлайн-присутствие — общий sorted set, время Redis, TTL логики 180 секунд.
  Heartbeat любого устройства продлевает присутствие; очистка атомарная.
* LiveKit передаёт медиа независимо от API. Авторизация личного звонка читает
  общие данные; ошибка Redis не трактуется как запрет участия и не удаляет участников.
* Сбор статистики и сверка прав LiveKit выполняются лидерами с обновляемой lease.
  Статистика публикуется в Redis для чтения любым процессом. Outbox и очистка
  signaling допускают несколько исполнителей благодаря атомарным операциям.
* Кеши неизменяемых SVG и конфигурация остаются локальными. Лимиты запросов уже
  общие в Redis. Ограничение одновременных загрузок локальное: 4 на процесс,
  максимум 16 при четырёх процессах, плюс ограничения nginx.

## Ресурсы и диагностика

По умолчанию `TESCORD_DB_POOL_SIZE=5`, `TESCORD_DB_MAX_OVERFLOW=5`,
`TESCORD_DB_POOL_TIMEOUT=5`: не более 40 соединений API при четырёх процессах.
Миграции запускаются отдельным шагом деплоя. Инициализация защищена PostgreSQL
advisory lock. Redis использует noeviction и AOF everysec. Денежные операции и
предметы не зависят от сохранности Redis; после аварии Redis возможно потерять
последнюю секунду signaling. Полная потеря Redis требует восстановления соединений.

Readiness проверяет PostgreSQL и Redis, возвращает 503 при отказе зависимости;
`X-Kva-Worker` показывает PID обслужившего процесса. `infra/logging.json` добавляет PID
к логам. Завершение worker ограничено 15 секундами, systemd — 25 секундами.

## Проверки

`integration/cluster_smoke.py` работает с четырьмя отдельными API на 8101–8104:
заявка/принятие, сообщение через третий процесс, присутствие, звонок с несколькими
устройствами, восстановление на другом процессе, групповой голос и mute,
одновременная покупка и подарок. Только локальная тестовая БД; тестовые учётные
данные записываются вне репозитория в текущий каталог `cluster-fixture.json`.

`KVA_CLUSTER_FAILURE_TEST=1` дополнительно убивает тестовый процесс 8103 и
приостанавливает отдельный тестовый Redis на 127.0.0.1:16379 на 8 секунд.
Не использовать этот порт для рабочего Redis. Остальные тесты переходов:
`KVA_TEST_REDIS_URL=redis://127.0.0.1:16379/0 pytest tests/test_cluster_state.py`.

Откат количества процессов: заменить `--workers 4` на `--workers 1` в override
systemd, `systemctl daemon-reload && systemctl restart tescord-backend`.
Оставить новый backend и общее Redis-состояние; откат данных не требуется.
Откат на старый backend с локальным signaling требует одного worker и прерывает
текущие управляющие соединения звонков.

## Проверенный выпуск 2026-10-19

131 существующий backend-тест и 5 новых Redis-тестов прошли. Четыре отдельных
процесса подтвердили доставку событий и атомарные повторы операций. Принудительная
остановка процесса и 8-секундная пауза Redis проверены на локальном стенде.
Дополнительно с настоящим `uvicorn --workers 4` проверены покупка одновременно
со списанием администратора, подарок одновременно с применением и четыре
одновременных принятия одной ссылки приглашения. Результаты согласованы.

Браузерный тест LiveKit подтвердил двусторонний аудиопоток, камеру, демонстрацию,
повторное подключение управляющего WebSocket и завершение звонка.
Контрольные 160 запросов `/api/me`, параллельность 16, локальный Windows-стенд:

| Процессы | Запросов/с | p50 | p95 | RSS процессов |
| --- | --- | --- | --- | --- |
| 1 | 243 | 57 мс | 100 мс | 158 МБ |
| 4 | 410 | 34 мс | 55 мс | 582 МБ |

Это сравнение на локальном компьютере, не прогноз производительности VPS.
Установщики Windows 0.5.2 и Android 0.3.2 (versionCode 6) собраны с актуальным
интерфейсом. Проверены Electron, WebView-мост, Android lint и прежняя подпись APK.
Проверка фоновых звонков на физическом Android-устройстве остаётся отдельной задачей.
